# 영역별 코드베이스 조사

기능 추가가 아니라 **설명 가능한 코드베이스**를 목표로, 영역을 하나씩 훑어 문제를 목록화한 기록이다.

각 영역은 파일 두 개가 짝을 이룬다.

| | 위치 | 역할 |
|---|---|---|
| 조사 문서 | `docs/issues/{영역}.md` | 상수 인벤토리, 충돌 점검, 근거(파일:라인)를 붙인 문제 목록 |
| 이슈 스크립트 | `scripts/issues/{영역}.sh` | 위 결과를 GitHub 이슈로 만드는 `gh` 명령. 한 번만 실행한다 |

## 이슈 메타데이터

우선순위(P0~P4)와 규모(S/M/L)는 **조직 Issue field**로 관리한다. `gh issue create`에는 필드를 지정하는
플래그가 없으므로 생성 후 UI에서 지정한다. 이슈 제목의 `[P1]` 접두사가 그 값을 그대로 알려준다.
라벨로 중복해 두지 않는다. 두 곳에 있으면 반드시 어긋난다.

`area:*` 라벨만 저장소 라벨로 둔다. 영역 구분은 이 저장소에서만 의미가 있어서
여러 저장소에 걸치는 조직 필드로 올리기에 맞지 않는다. 각 영역 스크립트가 자기 것만 만든다.

이슈 간 의존은 `--blocked-by`로 건다. 스크립트가 생성된 이슈 번호를 받아 다음 이슈에 넘기므로
실행 순서를 바꾸면 안 된다.

## 문서에 쓰는 것과 안 쓰는 것

조사 문서는 **특정 시점의 스냅샷**이다. 발견 당시의 코드 상태를 근거와 함께 박제하는 것이 목적이므로,
작업이 진행돼도 소급해 고치지 않는다. 코드 근거는 조사 시점 커밋에 고정한 permalink로 건다.

반대로 **결정과 트레이드오프는 여기 쓰지 않는다.** 조사는 "무엇이 문제인가"까지고,
"그래서 어떻게 하기로 했는가"는 아래로 간다.

- 점수 상수의 근거와 출처 → `docs/SCORING.md` (+ 사용 지점 코드 주석)
- 그 외 정책·구조·성능·배포 판단 → `docs/decisions.md`
- 결정에 이르는 논의 과정 → 해당 GitHub 이슈 코멘트 (결론은 이슈 본문 맨 아래에 덧붙인다)
