# 구현 로드맵

2026-11-24에 정한 방향(`docs/decisions.md`)을 구현하는 순서다. 화면 기준은 `docs/mockup/`, 기준값 근거는
`docs/SCORING.md`에 있다. 단계마다 끝나는 조건을 적어 두고, 끝나면 이 문서의 상태를 고친다.

## 작업 방식

- 단계 안의 작업 단위마다 `dev`에서 브랜치를 따고(`feat/…`, `fix/…`, `refactor/…`, `test/…`, `docs/…`), 끝나면 `dev`로 합친다.
- 기능에는 테스트를 같이 넣는다.
  - 도메인 로직(점수, 맑은 구간 찾기, 패턴 분류, 순위)은 단위 테스트로 경계값까지 확인한다.
  - API는 `@SpringBootTest` 통합 테스트로 확인한다. MySQL과 Redis는 Testcontainers로 띄운다.
  - 외부 API(Open-Meteo, MET Norway, Gemini, 길찾기)는 기록해 둔 응답으로 대체하고 실제로 호출하지 않는다.
- 코드를 바꾼 커밋 전에는 `./gradlew test`를 통과시킨다.

## 1단계. 테스트 기반과 정리

- Testcontainers, 외부 API 대체 수단을 갖춘 테스트 기반을 만든다.
- 지금 엔진의 동작을 고정하는 테스트를 먼저 쓴다. 바꿀 때 무엇이 달라지는지 보이게 하기 위해서다.
- 끝나는 조건: `./gradlew test`가 로컬에서 외부 네트워크 없이 통과한다.

상태: 2026-11-24 완료. 테스트 150개가 통과한다. 구성과 버린 대안은 `docs/decisions.md`의
"테스트 기반: Testcontainers와 RestTemplate 가로채기"에 있다. Docker가 떠 있어야 하고, 이미지를 처음 받을 때만 네트워크를 쓴다.

테스트를 쓰면서 코드만 읽어서는 알 수 없던 동작이 확인됐다. 고치지 않고 지금 동작 그대로 고정해 두었다.

- 예보 호출이 실패하면 분석 API와 예보 API가 캐시 오류 문구를 담은 400을 준다. 클라이언트가 실패를 `null`로 돌려주는데
  예보 캐시가 `null`을 저장하지 못해서다. 구름 100%로 0점을 주거나 빈 목록을 주는 분기에는 닿지 않는다.
  (`StargazingApiTest`)
- 예보의 Redis 만료 시간은 `CacheConfig`에 적힌 1시간이 아니라 기본값 10분이다. (`WeatherForecastCacheTest`)
- 광해 최근접 조회는 쿼리 안의 좌표 순서가 두 가지로 섞여 있어도 실제 MySQL 8.0에서 가장 가까운 격자점을 고른다.
  (`LightPollutionRepositoryTest`)
- 응답의 일출, 일몰, 월출, 월몰은 그 날짜의 값이 아니라 요청 시각 뒤에 처음 오는 값이다. (`AstronomyCalculatorTest`)
- 달 위상각의 부호 규약(0이 보름, 음수가 차오르는 달)은 USNO의 2026년 1월 위상 시각과 맞는다. (`AstronomyCalculatorTest`)

## 2단계. 1시간 단위 예보

- Open-Meteo 클라이언트를 만들고, 장애 시 MET Norway로 넘어가게 한다.
- 캐시 키는 모델 격자 셀과 모델 실행 시각으로 잡는다.
- 끝나는 조건: 임의 좌표의 다음 7일 시간별 총운량, 층별 운량, 습도, 이슬점, 시정을 내부 모델로 받을 수 있다.

상태: 2026-11-24 완료. `WeatherDomainService.getHourlyForecast(lat, lon)`이 지금부터 168시간의 시간별 값을 돌려준다.
모델, 캐시 단위, 폴백을 어떻게 정했는지는 `docs/decisions.md`의 "시간별 예보 수집: 모델, 캐시 단위, 폴백"에 있다.

- MET Norway로 넘어간 경우에는 1시간 간격인 앞쪽 61시간쯤만 있고 시정이 없다.
- 기존 분석, 예보, 추천 API는 아직 OpenWeather를 쓴다. 3단계에서 옮긴다.
- 배포할 때 환경변수 `MET_NORWAY_USER_AGENT`를 넣어야 폴백이 동작한다.

## 3단계. 시간대 추천 엔진

- `docs/SCORING.md`의 제안값을 확정하고 사용 지점에 출처 주석을 단다.
  - 박명 -12°와 -18°
  - 관측 가능한 구름 30% 이하
  - 달 위상 함수
  - 습도 80% 이상이면 이슬 주의
- 시간별 점수, 맑은 연속 구간 찾기, 밤 패턴 분류(밤새 맑음, 늦게 갬, 초저녁만 맑음, 흐렸다 갬, 밤새 흐림)를 만든다.
- 내 장소와 기본 추천 명소를 이동 시간과 함께 순위로 매긴다. 이동 시간은 우선 직선거리로 추정하고 길찾기 API는 6단계에서 붙인다.
- 오늘 밤 추천 API와 날짜별 추천 API를 만든다.
- 끝나는 조건: 목업의 세 시나리오(좋은 밤, 보름달 밤, 전국 흐림)를 고정 데이터로 재현하는 통합 테스트가 통과한다.

상태: 2026-11-24 진행 중.

- 끝난 것: 기준값 확정과 출처 주석, 시간별 점수, 맑은 연속 구간, 밤 패턴, 추천 등급(`NightAssessmentEngine`).
- 남은 것: 장소 후보 모으기와 순위, 이동 시간 추정, 오늘 밤 추천 API와 날짜별 추천 API, 세 시나리오 통합 테스트.

## 4단계. 광해 데이터 재구축

- NASA Black Marble 연간 자료로 래스터를 다시 만들고, 내부 기준을 연속값으로 바꾼다. Bortle은 라벨로만 쓴다.
- 지도용 래스터 타일을 만든다.
- 끝나는 조건: 출처 없는 레이디언스 → Bortle 표가 코드와 스크립트에서 사라진다.

## 5단계. 새 프론트엔드

- 메인을 오늘 밤 추천으로 바꾼다. 글꼴은 Noto Sans KR, 다크 단일 테마로 한다.
- 지도를 MapLibre로 바꾸고, 밤 불빛, 구름, 일반 지도 레이어를 둔다.
- 설정(간단히/자세히, 몇 시까지, 얼마나 멀리)과 "추천 기준과 출처" 화면을 만든다.
- PWA로 설치할 수 있게 한다.
- 끝나는 조건: 목업의 화면 흐름을 실제 API로 따라갈 수 있다.

## 6단계. 구름 지도와 이동 중 재판단

- 구름 레이어용 격자 예보 API를 만든다.
- 길찾기 경로와 구간별 통과 시각을 붙인다.
- 출발 후 도착 시각의 예보가 나빠지면 대안 장소를 제안하는 알림을 보낸다. 웹 푸시부터 시작한다.

## 7단계. 이번 주 추천과 알림

- 요일별 추천과 예보 신뢰도를 붙인다.
- 저장한 장소에 좋은 밤이 오면 미리 알린다.

## 배포

만든 것은 실제로 배포해서 쓴다. 백엔드는 OCI, 프론트엔드는 Vercel에 올린다. 2026-11-24 기준 상태는 다음과 같다.

- `.github/workflows/deploy.yml`은 `dev`에 push하면 EC2로 배포하던 AWS 시절 파이프라인이다. OCI로 바꿔야 한다.
- OCI 쪽은 VM 한 대에 Caddy, 앱, MySQL, Redis를 compose로 띄우는 구성이 `infra/oci/deploy/`에 있다.
  아직 저장소에 올라가 있지 않고, 배포는 손으로 한다.
- 배포 빌드는 테스트를 건너뛴다(`-x test`).
- 프론트엔드는 이 저장소 밖에 있다.

정해야 할 것:

- 백엔드를 언제부터 올릴지. 새 API가 생기는 3단계가 끝난 뒤가 첫 시점으로 적당하다.
- OCI 배포를 GitHub Actions로 자동화할지, 지금처럼 손으로 할지.
- 배포 전에 CI에서 테스트를 돌릴지.
